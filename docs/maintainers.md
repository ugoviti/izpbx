# Maintainers: component updates and releases
Component versions and checksums live in `izpbx-asterisk/versions.env`; the FreePBX modules pre-downloaded into the image in `izpbx-asterisk/build/freepbx-modules.txt`. In `izpbx-asterisk`, `build/` holds only what the image build uses; maintainer tools are in `izpbx-asterisk/tools`, development notes (build and run from the sources) in [development.md](development.md).

Check for updates, then apply them (versions and sha256 together; when Asterisk changes, its bundled pjproject and jansson follow the release tarball):
```
izpbx-asterisk/tools/make-updates.sh            # report (exit 10 when updates are available)
izpbx-asterisk/tools/make-updates.sh --apply    # write versions.env and freepbx-modules.txt
```
Then rebuild, run `izpbx-asterisk/tests/run.sh all-done` and commit. `compose.yml` and `default.env` of a deploy are in `izpbx-asterisk/rootfs/usr/local/share/izpbx/deploy` (in the image, for `izpbx-deploy`, see [izpbx-deploy.md](izpbx-deploy.md)); after a change of `default.env` run `izpbx-asterisk/tools/deploy-sync.sh`: it writes the list of every variable `default.env` ever had and, from the tags, the files of every release (the base of the upgrade); `lint.sh` (pre-commit) fails when they are out of date, `make-release.sh` runs it by itself. Versions: write as few as possible. The docs use the series tag of the image (`izpbx-asterisk:22.17`, with `docker run --pull always`; `izpbx-deploy` writes the exact version of the image in `.env`) or no version (`mariadb:10.11`, `${IZPBX_VERSION}`); `compose.yml` has none (`IZPBX_VERSION` and `MARIADB_VERSION` are required in `.env`). The exact versions left are `IZPBX_VERSION` and `MARIADB_VERSION` of `default.env` and the download URLs of [izpbx-deploy.md](izpbx-deploy.md). At every release `tools/make-release.sh` moves every reference to a version of the series (`izpbx-asterisk:X.Y.N`, `IZPBX_VERSION=X.Y.N`, `${IZPBX_VERSION:-X.Y.N}`, `.../ugoviti/izpbx/X.Y.N/`, also one left behind by an older release) in the README, `docs/` and the deploy files, and stops before the commit if `izpbx-asterisk/tools/check-versions.sh` still finds one that is not the new version; the same check runs in `lint.sh` (pre-commit) and in P7-09, also for every `mariadb:X.Y.Z` against `MARIADB_VERSION` (changed by hand). Versions in prose ("from 22.17.0") are history and stay. The tests read the current version from `default.env`. A new series (22.18) changes the series tags of the docs by hand. A variable renamed in `default.env` goes in `izpbx-asterisk/rootfs/usr/local/share/izpbx/deploy/renames.tsv` (`OLD NEW VERSION`), so `izpbx-deploy upgrade` moves its value. When FreePBX, Asterisk, FOP2 or the Debian base change, go through [workarounds.md](workarounds.md): each workaround for an upstream defect says how to tell whether it is still needed.

Release the next patch version (`22.17.0` → `22.17.1` …) from `main` (or `release/X.Y` for a maintenance series):
```
izpbx-asterisk/tools/make-release.sh              # dry run: the CHANGELOG entry and the changes, nothing written
izpbx-asterisk/tools/make-release.sh --commit     # review the entry in $EDITOR, commit "X.Y.Z release" and tag X.Y.Z
izpbx-asterisk/tools/make-release.sh --push       # as --commit, then push the branch and the tag (starts the izpbx-release workflow)
izpbx-asterisk/tools/make-release.sh --rc --push  # release candidate X.Y.Z-rcN of the next version: only the tag, from any branch (pushed with the branch)
```
The tag starts `izpbx-release`: its `amd64` job publishes the tags in the Gitea registry with the amd64 image (test it right away), then the `arm64` job (tags of `main` only, 20.16 stays amd64) builds the arm64 image under QEMU (~35 min without cache) and turns the same tags into amd64 + arm64. An `izpbx-promote` run before the `arm64` job ends copies the amd64 image only: run it again afterwards. With `github` and `github_release` (both checked by default) `izpbx-promote` also creates the GitHub release page of the tag from its `CHANGELOG.md` entry (`tools/forge-release.sh`: `-rcN` tags as pre-releases, the GitHub "Latest" only for the highest X.Y.Z, a release already there is updated; `GH_PUSH_TOKEN` needs Contents: write). The Gitea release page of every tag is the last job of `izpbx-release`, once the images are built (`izpbx-release-page` does it by hand for an existing tag; secret `RELEASE_TOKEN` only when the automatic token cannot write releases). `izpbx-dev` builds arm64 too with its `arm64` option.

Write the changes under `## [Unreleased]` in `CHANGELOG.md` while you work: the release dates that block and adds one line per updated component by itself. If nothing was written there, the draft comes from the commit subjects, or from Claude Code with `--ai` (`claude -p`); review it before confirming. GitHub and Docker Hub are updated separately with the `izpbx-promote` workflow (Gitea > Actions > izpbx-promote > Run workflow): a `version` publishes that tag (the default `last` is the most recent tag, rc included, written in the log of the first step; `latest` is moved only for 20.16.x, ignored with a warning otherwise) (git tag and branch on GitHub, image on Docker Hub, with branch `main` the Docker Hub overview from its README, made by `izpbx-asterisk/tools/readme-dockerhub.sh`); an empty `version` only pushes the branch to GitHub (and with `main` the overview). The README must stay under the 25000 bytes of Docker Hub: `izpbx-asterisk/tests/lint.sh` checks it.
