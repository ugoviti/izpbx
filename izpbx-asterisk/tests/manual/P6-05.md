# P6-05 — Weekly rebuild of both branches (Gitea)

The automated test P6-05 checks the matrix of
`.gitea/workflows/weekly-rebuild.yml` and runs its "resolve latest release"
step on a scratch repository. This procedure checks the real run: the
`release/20.16` branch exists on Gitea and a manual run produces the images
of both branches.

## 1. Create `release/20.16` (V4)

From the tag `20.16.22`, with its own CI tooling (Rocky Linux checks):

```sh
git fetch --tags origin
git branch release/20.16 20.16.22
git push origin release/20.16
```

Nothing else changes on that branch: from now on it gets security fixes only,
until 2027-01-01.

## 2. Manual run

Gitea schedules use the workflow of the default branch, so the matrix is the
one on `main`: run it once `feature/22.17` is merged, or by hand from
`feature/22.17` (Repository > Actions > izpbx-weekly-rebuild > Run workflow,
branch `feature/22.17`).

Expected:

- two jobs, `rebuild release/20.16` and `rebuild main`;
- `rebuild release/20.16`: green, image `izpbx-asterisk:20.16.22-<YYYY>-W<WW>`
  (and `-<run_number>`) in the Gitea registry;
- `rebuild main`: green; before the first 22.17.x tag it logs
  "main: no X.Y.Z release tag yet, nothing to rebuild" and builds nothing,
  after it the image `22.17.<n>-<YYYY>-W<WW>`;
- no tag `latest`, `20.16`, `22.17` moved; nothing on Docker Hub;
- two Matrix notifications, one per branch.

Result: report it to close P6-05 in the checklist.
