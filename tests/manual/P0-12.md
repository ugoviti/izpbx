# P0-12 — Commercial modules after the restore (manual)

Informational check (D24): the migration goes ahead when commercial modules
are installed and only warns that they must be reactivated. This procedure
collects the evidence the README (P7-01) needs: what state a commercial module
is in after the restore on izPBX 22.17 (a non-distro FreePBX 17), and which
steps bring it back.

It is manual because it needs a real commercial license and deployment ID
(Sangoma portal), which the automated tests do not have.

## What you need

- A working izPBX **20.16.22** with at least one licensed commercial module
  (for example sysadmin, endpoint, or any paid module), registered to a
  deployment ID.
- Access to the Sangoma portal account that owns that deployment.
- A spare host or VM for the 22.17 test. **Never run this on the production
  data volume:** work on a copy.

## Steps

### 1. Record the state on 20.16.22 (source)

```bash
docker exec izpbx fwconsole ma list > before-ma-list.txt
docker exec izpbx fwconsole ma list | grep -iE 'commercial|licen'
```

In the web UI, note the deployment ID and license status
(*Admin → System Admin → Activation*, or *Admin → Module Admin*). Note too
the outputs of `php -v` (ionCube loader version) and `hostname`, and the MAC
address of the container's network interface: licenses can be tied to the
machine identity.

### 2. Copy the data

Stop the 20.16.22 container and copy the data volume (`/data`) to the test
host. Keep the original untouched.

### 3. Start izPBX 22.17 on the copy

Start the 22.17 image on the copied volume with the same `.env`. The
migration runs on its own. Keep the migration log and check that it contains
the commercial module warning (D24) and that the migration did **not** stop
because of it.

### 4. Record the state after the restore

```bash
docker exec izpbx fwconsole ma list > after-ma-list.txt
diff before-ma-list.txt after-ma-list.txt
```

For every commercial module, note:

- the status in `fwconsole ma list` (Enabled / Disabled / Broken / not
  installed, license state);
- whether its web pages open or show an activation / license error;
- whether the deployment ID shown in the UI is the same as in step 1.

### 5. Reactivate

Follow the steps needed to bring the module back (for example, reactivate
the deployment from *System Admin → Activation*, update the license on the
Sangoma portal if the machine identity changed, then
`fwconsole ma refreshsignatures`, `fwconsole reload`). Write down **exactly**
which steps were needed and in what order: they go into the README (P7-01).
